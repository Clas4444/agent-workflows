## Demonstrated platform defect

**CONFIRMED_BUG, P2 — source-pin omission below a cache-named ancestor.**
The declared contract in [testing procedure](../procedure.md) says edited verification
inputs cannot validate as current. `input_snapshot()` filtered `__pycache__` using
absolute path components. Exporting the repository beneath a parent named
`__pycache__` therefore excluded the entire recursive source scope, rather than
only bytecode directories inside the repository.

Minimal operational sequence, using disposable copies:

1. Export the base revision into `<fixture>/__pycache__/repo`.
2. Run the actual eleven-gate verification campaign and retain its report.
3. Append a harmless comment to `scripts/catalog.py` after the campaign.
4. Verify the retained report against that edited checkout.

Before repair all eleven actual gates passed, but only **12 files** were pinned;
the edited source was absent. The stale verification returned **exit 0**, saying
`PASS: session and verification inputs match`. This is a real false acceptance,
not a mock-based assertion or an invented vulnerable fixture implementation.

The focused regression ran **9 tests with 1 failure before repair**. The root fix
checks `path.relative_to(repo).parts`, preserving bytecode exclusion only inside
the declared repository boundary. The same focused suite then passed **9/9** on
Python 3.12 and 3.14. A fresh actual exported campaign pinned **335 files**; fresh
verification returned **0**, and the same post-campaign source edit returned **1**
with a stale-input diagnostic. An additional control confirms real repository
bytecode stays excluded while source remains pinned.

The exported baseline suite discovered 246 tests with one Windows skip; the
repaired export discovered 248 with one skip. These counts describe those specific
exports and do not substitute for the final working-tree campaign below. The
unit regression injects successful command results to isolate pin logic; the
separate actual CLI campaigns establish the operational false PASS.

### Narrowed response-only campaign v2

The next protocol is a separate, narrower experiment, not a retroactive relabeling
of the original campaign. It calls the real model to generate responses; the parent
materializes only the named files and runs the frozen checker. Code responses must
include actual replacement code and discoverable passing regression tests; office
responses must contain the report object and briefing text. Models must not claim
to have executed commands or reopened files in this generation-only mode.

Two task cases × two conditions × two repetitions give **8 planned real-generation
trials**. Order is counterbalanced:
`code-A-1, code-B-1, office-B-1, office-A-1, code-B-2, code-A-2, office-A-2, office-B-2`.
A receives the common task only; B additionally receives the selected exact Loop
instruction payload. The task, model/configuration, tool profile, authority,
180-second attempt ceiling and acceptance checker are otherwise held equal where
observed. Fresh homes, workspaces and histories prevent attempt-to-attempt leakage;
startup/context evidence must establish baseline discovery isolation. A flag alone
is insufficient. Explicit instruction supply does not establish native discovery.

```text

python scripts/benchmark_cases.py prepare --case code --root <new-fixture>
python scripts/benchmark_cases.py check --case code --root <completed-fixture>
```

into its named files and use the unchanged checker; record the actual model and
permission profile. Generated code must be treated as untrusted executable code
